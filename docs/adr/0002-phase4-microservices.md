# ADR 0002 — Phase 4 (ТЕНТАТИВНО): переход на микросервисы

Status: Proposed / Optional / Conditional. Выполнять ТОЛЬКО при реальном триггере и ПОСЛЕ Phase 3 (гексагон + фитнес-функции). По умолчанию — остаёмся «модульным монолитом» (результат Phase 3), который уже microservice-ready.

## Главная мысль: не торопиться
Микросервисы добавляют распределённые проблемы (сетевые сбои, eventual consistency, распределённые транзакции, ops/деплой, observability, версионирование контрактов). Большую часть пользы (изоляция, чёткие границы, независимая разработка) даёт уже **модульный монолит** из Phase 3. Поэтому Phase 4 — НЕ цель сама по себе.

**Дробим сервис только при конкретном драйвере:**
- нужна независимая масштабируемость части (напр. LLM-нагрузка, тяжёлый conveyor);
- отдельное владение командой / релизный цикл;
- другой рантайм/стек или изоляция по безопасности/комплаенсу;
- разный профиль надёжности (фоновые воркеры vs онлайн-API).

## Почему Phase 3 — обязательный пролог
Гексагон (ports & adapters) делает разделение **инкрементальным и обратимым**: у каждого bounded-context есть порт. Сегодня порт реализует in-process адаптер (монолит), завтра — gRPC-клиент-адаптер к вынесенному сервису. Домен не меняется. Это паттерн **strangler fig**: выносим по одному контексту, без big-bang.
Готовые швы уже есть: `reports_llm_ms` (УЖЕ отдельный gRPC-сервис), `emplacc-mcp` (отдельный процесс), conveyor-домен, будущие уведомления.

## Транспорт (то, в чём просили ориентир)
- **Синхронный внутренний (service↔service): gRPC.** Уже используется (emplacc↔reports_llm_ms). Контракт-first на protobuf, строго типизирован, быстрый — это и есть «нормальный» транспорт для Go-микросервисов. Один .proto = источник правды (gRPC + grpc-gateway для REST + генерация TS-типов).
- **Асинхронный / события: брокер сообщений.** Для развязки и event-driven (наш SSE `EventHub` эволюционирует в реальную шину). Выбор:
  - **NATS / NATS JetStream** — лёгкий, Go-native, простой ops; дефолтный выбор для старта.
  - **Redis Streams** — уже есть Redis, минимум новой инфры; ок для умеренных объёмов.
  - **Kafka** — если нужен большой объём/реплей/долгое хранение лога; дороже в эксплуатации.
- **Внешний / edge: HTTP(S) REST через API Gateway / BFF.** Фронт ходит в gateway; внутрь — gRPC. v2-envelope `{data,meta,error}` остаётся контрактом edge-слоя. Можно grpc-gateway, чтобы не дублировать.

## Архитектурные паттерны (минимальный обязательный набор)
- **Границы = bounded contexts** из Phase 3 (DDD). Не дробить «по слоям», только по доменам.
- **Database per service** — каждый сервис владеет своими данными; никакого общего доступа к чужим таблицам (иначе это распределённый монолит).
- **Reliable events: transactional outbox** — публикация событий в одной транзакции с записью в БД (у нас уже есть transactional event-log conveyor — это почти готовый outbox).
- **Кросс-сервисные транзакции: saga** (хореография через события или оркестрация) вместо распределённых транзакций.
- **Resilience: таймауты + ретраи + circuit breaker** на каждый исходящий вызов (`internal/resilience`).
- **Observability обязательна:** распределённый трейсинг (OpenTelemetry), метрики (Prometheus), корреляция request-id — без этого распределёнку не отлаживать. (Закладываем ещё в Phase 3.)
- **Контракты versioned**, обратная совместимость; контрактные тесты между сервисами.
- **Деплой:** контейнеры (есть docker-compose) → оркестрация (k8s/Rancher для прод); конфиг и секреты вне образа.

## Предлагаемый путь (если решим делать)
1. Довести Phase 3 (порты + observability + resilience) — без этого Phase 4 преждевременен.
2. Выбрать ПЕРВЫЙ кандидат на вынос — самый автономный контекст (кандидаты: уведомления, conveyor, или формализовать уже-отдельные reports_llm_ms/mcp как часть карты). Один сервис, strangler-fig.
3. Зафиксировать его gRPC-контракт; реализовать gRPC-адаптер для его порта; вынести модуль в отдельный сервис + БД; gateway маршрутизирует.
4. Добавить брокер (NATS/Redis Streams) для его событий через outbox.
5. Оценить результат (сложность vs выгода) ПЕРЕД выносом следующего. Возможно, на одном-двух сервисах и остановиться.

## Вывод
Phase 4 держим как опцию «по требованию». Инвестиции, которые окупятся в любом случае (даже если останемся монолитом): чёткие порты (Phase 3), observability, resilience, контракты на protobuf. Они и есть «нормальная микросервисная архитектура», просто внедряются заранее и постепенно.
